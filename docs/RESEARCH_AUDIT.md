# RESEARCH AUDIT — Research Report v1 (2026-10-29), "Verifiable Secure Data Destruction in Java"

**Audit type:** Phase 1 independent research audit (desk research only; no code was built or run).
**Date of audit:** 2026-11-10.
**Method:** Each claim in the report was treated as unproven and checked against the strongest source reachable: NIST CSRC, the OCP and NVM Express specification documents, RFC/C2SP primary texts, Oracle/OpenJDK API documentation, publisher artifact metadata (Maven Central), project source/README pages, and peer-reviewed papers. Vendor blogs and legal-firm summaries are labelled [S] (secondary) wherever they are the best evidence obtained. Every URL below was returned by a search/fetch tool during this audit; none was reconstructed from memory. Where a claim could not be checked against a readable source, it is marked **UNVERIFIABLE / TO VERIFY** rather than repeated as fact.

**Honest scope limit (applies to the whole project):** user-space Java cannot verify physical flash. Nothing in this audit, and nothing the planned library can do, establishes that NAND cells were erased. All verification discussed here is **logical-level only**: process memory, heap dumps, files, and bytes visible through OS/JVM interfaces.

**Verdict tally (26 rows):** CONFIRMED 13 · PARTLY 9 · UNVERIFIABLE 4 · REFUTED 0 as whole-row verdicts — but two load-bearing *sub-claims inside* PARTLY rows are refuted (the report's definition of NIST "validation", and its claim that C-12 has "no primary source"). See §(d).

## (c) Revised novelty assessment (N-1 … N-5)

### N-1 — Control-validated canary validation: **DEFEND, reworded** (still the strongest claim)
No Java tool found in this audit performs post-destruction validation in which the measurement itself is validated by **positive and negative controls** — a canary that must be found before destruction (positive control) and an unrelated pattern that must never be reported (negative control) — yielding a *measured false-assurance rate* rather than an asserted one. That combination appears genuinely unoccupied. Two mandatory rewordings:
- Per C-2, what the canary scan produces is strong **verification**; "validation" in Rev. 2 is the subsequent decision. Rename the claim accordingly (e.g. "control-validated verification strong enough to support a non-rubber-stamp validation decision").
- Scope the gap: independent read-back verification exists at drive level (Blancco Drive Verifier, AAD-50's log polling, IEEE 2883-2022 Clause 7 sampling). The defensible claim is **Java / logical / in-process** scope only.

### N-2 — Empirical Java secret-pattern × GC/JIT leakage matrix: **DEFEND as an extension, not a discovery**
The underlying phenomenon (C-12) is established by peer-reviewed work — but only for SerialGC and G1GC, a decade ago. A systematic, measured matrix across secret representations (byte[] / char[] / String / off-heap / Destroyable) × collectors (Serial / Parallel / G1 / ZGC / Shenandoah) × JIT tiers, with found/not-found rates, would be a real contribution *if the Phase 2 experiments actually deliver it*. Novelty here is contingent on execution, not on the idea.

### N-3 — Commit/rollback destruction transactions: **REWORD (narrow substantially)**
Every ingredient is established prior art: write-ahead journals and two-phase commit (decades old), vault/escrow restore, and scheduled-deletion grace windows (AWS KMS 7–30 days, §(b).7). The only defensible novelty is the specific coupling: **rollback gated on failed post-destruction validation**, with a witnessed ABORTED event recorded *before* any restore — because restoring first and logging later would let rollback hide validation failures. Claim that coupling, nothing broader. Also honour the standing rule: **never promise restore after COMMIT.**

### N-4 — Witness-cosigned Merkle log + offline verifier in Java: **REWORD / drop the broad form**
Merkle transparency logs with witness cosigning and offline verification are a mature, standardised pattern (RFC 6962/9162, C2SP tlog-checkpoint/tlog-cosignature, Trillian/Tessera, CONIKS/Parakeet), and hash-chained logs alone are admittedly not novel (K-7, K-9 both have them). The broad claim should be dropped. The narrow claim that may survive: to this audit's search, the first application of a **witness-cosigned** transparency log specifically to **Java destruction evidence**, with an offline verifier — an integration/combination contribution, and it should be presented as such.

### N-5 — Evidence schema mapped to Rev. 2 verification-vs-validation: **DROP as a novelty claim**
Rev. 2's own Appendix C form already separates the verification method from a validation field and provides a concurrence/signature block. Mapping a JSON schema onto a published form is sound engineering and worth doing — it is not research novelty. Retain it as a design requirement; remove it from the novelty list.

## (d) Errors in the report (plain list)

1. **The definition of "validation" is wrong (load-bearing).** The report treats validation as a data-absence check ("target data actually sanitized"). In Rev. 2, verification determines the outcome of the sanitization technique; **validation is a risk-based decision** that reviews the verification results against the data's sensitivity and approves, rejects, or escalates. Consequence: the project's canary machinery is *verification* (unusually strong verification), and the thesis sentence should be rewritten as "automate verification strong enough that validation is not a rubber stamp" — otherwise every standards-literate reviewer will flag §1/§2.
2. **The certificate field list is incomplete and vendor-sourced.** Rev. 2 Sec. 4.6 / Appendix C is **media-centric**: manufacturer, model, serial number, property number (if assigned), media type, media source, sanitization method, sanitization technique, tool used **including version**, verification method, and personnel (who performed it, when, where, signature) — and the Rev. 2 form adds a validation field, a concurrence block, media operational/damaged status, and destination. A file/object-level Java tool cannot copy these fields; it must explicitly *map* them (e.g. media serial → volume/file identity) and say what has no analogue.
3. **C-12's sourcing note is false.** "[S] StackOverflow consensus, no primary source" — peer-reviewed primary sources exist (Pridgen et al., HICSS-50 2017; DFRWS EU 2017). The claim survives, stronger, properly cited.
4. **C-7 is imprecise in two places.** RFC 9162 is **Experimental**, not Standards Track. And C2SP checkpoints hash over the **RFC 6962** Merkle tree — the design text's "Merkle log per RFC 9162 hashing" needs correcting before it propagates into code and documentation.
5. **H3 (a Phase 2 "open question") is resolvable by reading.** The `jcmd` documentation settles `GC.heap_dump -all` semantics: it dumps all objects including unreachable ones, and requests a full GC *unless* `-all` is given. Conversely, the report understates the residual problem: even with `-all`, a heap dump contains *objects*, not raw freed-region bytes — stale copies in evacuated regions require /proc/<pid>/mem or core-dump scanning. — https://docs.oracle.com/en/java/javase/21/docs/specs/man/jcmd.html
6. **The competitor landscape omits shipped Java prior art.** Axon crypto-shredding extension (Maven Central, v2.0.0, 2023) and Bouncy Castle's Destroyable/zeroization support are absent from K-1…K-14, as are Hao & Clarke's Java Card prototype and KMS scheduled-deletion grace windows (prior art against §6.1's "optional GRACE" being presented as a design novelty).
